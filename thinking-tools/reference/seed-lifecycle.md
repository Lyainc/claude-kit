# Seed 생애주기 계약

이 문서는 #814의 공통 계약이에요. build-spec이 생성·변경을 소유하고, 종료 루틴은 이 계약을
사용해 승인된 종료 처리를 수행해요. Seed가 생애주기 원본이고, 관계 조회·next-goal·Seed board는
그 원본을 읽어요. UI 캐시나 GitHub 이슈 상태로 Seed 상태를 추정하지 않아요.

## 상태와 적용 범위

| 상태 | 의미 | 요구사항을 작업에 적용하는 조건 |
|---|---|---|
| 생애주기 없음 | 상태 미확인인 기존 Seed | 관련 본문은 읽을 수 있지만 적용 전 사용자 확인 필요 |
| `active` | 사용자가 활성화한 요구사항 | 현재 요청 범위에 속하고 철회·보류되지 않은 항목만 |
| `paused` | 재개 가능한 일시중단 | 사용자가 재개를 승인하고 `active`로 전환한 뒤 |
| `closed` | 종료된 결정 기록 | 자동 재개 금지. 선택한 요구사항을 새 Seed로 옮겨 별도 승인 |

경로를 명시하거나 그래프에서 발견한 것, next-goal 후보를 제안한 것만으로는 활성화·재개·범위
확장이 승인되지 않아요. 종료된 Seed는 결정 이유 조회, 충돌 검사, 설계 재사용에 계속 사용할 수
있어요. 이후 코드 변경은 과거 종료 결과를 자동 재판정하거나 변경하지 않아요.

## 저장 형식과 전이

템플릿 `skills/build-spec/templates/SEED_SPEC.yaml`이 필드 허용 목록을 소유해요.
아래 `{id, refs}` 표기는 필드 설명이에요. 실제 목록 항목은 들여쓴 block YAML로 작성해요.
별칭·태그·앵커·중첩 flow mapping은 지원하지 않으며 검증기가 명시적으로 거부해요.

- `lifecycle.state`: `active`, `paused`, `closed`.
- `lifecycle.outcome`: active/paused에서는 null, closed에서는 `completed` 또는 `discontinued`.
- `reason`, `approved_by`: 전환 이유와 실제 사용자 지시·확인 근거. 에이전트가 승인을 만들어
  적으면 안 돼요. 신규 활성화도 인터뷰에서 확정된 요청을 근거로 기록해요.
- `evidence.commit`: 검증 대상의 전체 Git SHA. 기록을 추가하는 커밋의 SHA와 구분해요.
- `evidence.items`: `{id, refs}` 목록. 각 refs는 그 항목을 확인한 코드·테스트·문서 위치 또는
  실행 결과 링크예요. 테스트를 실행하지 않았으면 실행했다고 쓰지 않아요.
- `withdrawn`: `{id, reason}` 목록. 원래 항목의 ID와 내용은 그대로 두고 철회만 별도 기록해요.

신규 Seed는 사용자가 확정한 요구사항으로 활성화해요. 미완성 초안의 조기 출력이 활성화 승인까지
포함하지 않으면 `paused`로 작성해요. 기존 상태 미확인 Seed는 사용자 확인 후에만 전환해요.
active ↔ paused, active/paused → closed는 실제 승인에 따라 처리해요. closed → active/paused는
허용하지 않아요. 종료 결과·완료 근거는 동결하고 새 작업에는 새 Seed와 출처를 사용해요.

`completed`는 철회하지 않은 **모든 constraints와 success_criteria**가 지정 커밋에서 충족되고,
항목별 근거가 있을 때만 가능해요. 남은 항목이 하나도 없이 전부 철회된 경우, 일부만 충족한 채
종료한 경우, 미충족 항목을 다른 Seed로 이관한 채 종료한 경우는 `discontinued`예요.
이관·이슈 닫힘·PR 병합은 그 자체로 충족 근거가 아니에요. 진행률·작업 일지·실행 로그는 계속
금지해요. 생애주기는 현재 결정 한 건이며 전환 이력을 append하는 배열이 아니에요.

## 승인과 변경 절차

1. 이름이 주어진 Seed만 메타데이터부터 확인해요. 관련 항목과 현재 코드·테스트를 읽고 처리안을
   만들어요. 발견, 읽기, 후보 제안, 요구사항 적용은 서로 다른 행위예요.
2. 상태 전환·철회·자식 영향·재연결을 구분해 제안해요. 기존 종료 확인과 함께 승인받을 수 있고,
   사용자가 이미 정확히 지시한 철회는 다시 묻지 않아요. 응답이 없으면 변경하지 않아요.
3. 수정 전 파일을 임시 파일에 보존하고 필드 값을 교체해요. 철회 항목은 원문을 보존해요.
4. `seed-lifecycle.py check <seed> --before <prior-file>`와 `seed-relations.py check <seed>`를
   실행해요. 검증 실패 시 수정안을 고치고, 외부 저장소 수정이 필요하면 그 위치를 보고해요.
5. Claude Code는 편집 훅도 사용하고 Codex는 동일 검증 명령을 명시적으로 실행해요. 기록된
   승인 문자열이 실제 인간의 승인인지 검증기가 판정할 수는 없어요. 에이전트가 대화 근거를
   확인해야 하고, 임의 파일 읽기나 도구 밖 편집까지 기술적으로 차단한다고 주장하지 않아요.

## 철회 영향과 관계

`relations.refines`는 부모 항목을 가리켜요. `refines_map`의 각 `{parent_item, child_items}`는
그 부모 항목이 자식의 어느 항목으로 구체화되는지 명시해요. 내용만으로 대응을 확정하지 않아요.
부모가 없는 독립 Seed의 `refines`와 `refines_map`은 비워요. 이전 부모 항목은 고정된
`provenance`로 보존하며, 현재 부모의 항목 참조로 남기지 않아요.

- 부모 전체 철회는 연결된 자식 모두를 재검토 대상으로 만들어요. 자식을 자동 철회하지 않아요.
- 일부 철회는 해당 부모 항목을 구체화하는 자식에만 영향을 줘요. 다른 유효 항목만 구체화하는
  자식은 계속 후보가 될 수 있어요.
- 유효·철회 항목이 섞인 자식은 명시적 대응이 충분하면 해당 자식 항목만 제외해요. 매핑이
  없거나 불완전하거나 `refines`가 비어 있으면 영향 불명으로 전체 자동 선택을 보류해요.
- 재연결은 별도 사용자 승인 후 부모·자식 양방향 링크를 함께 검증해요. 철회 승인은 재연결
  승인이 아니에요. 적절한 부모가 없으면 독립 Seed로 유지하고 이전 출처를 보존해요.
  유효한 자식의 소속이 부적절해졌다면 다른 적절한 Seed로 옮기는 안을 먼저 제안해요.
  새 부모는 실제로 묶어 관리할 필요가 있을 때만 제안하며, 확인 전 연결을 확정하지 않아요.
- `relations.transfers`의 `{seed, items}`는 자기 항목의 명시적 이관이에요. 도착 Seed에는
  `relations.provenance`로 원본의 정확한 파일·커밋·선택 항목을 남겨요.
- `relations.replaces`는 대체 파일을 명시해요. 출처 고정은 별도의 `provenance`가 맡아요.

## 버전 해석과 호환

신규 관계는 `relations.version: 2`이며 parent/children/depends_on/replaces/transfers는 정확한
파일 경로를 가리켜요. `provenance`는 `{seed, commit, items}`로 파일과 커밋까지 고정해요.
역사적 출처를 조회할 때 해당 커밋을 읽고, 읽지 못하면 미확인으로 표시해요.

생애주기와 관계 버전이 없는 구형 관계만 기존 `-vN` 최신 세대 해석을 유지해요. 명시적
생애주기를 가진 대상이나 종료 기록을 새 세대로 조용히 바꾸지 않아요. 관계 전환 때는 실제
해결된 파일과 양방향 링크를 검토해서 version 2로 기록해요. 일괄 전환은 하지 않아요.
구형 ID는 그대로 읽고, ID 전환은 기존 `seed-id-migrate.py`의 지원 범위와 검증을 먼저 확인해요.
역사적 커밋의 ID는 원본 표기 그대로 유지해요.
현재 ID 전환 도구는 생애주기·구조화된 항목 참조가 있는 파일의 이름 변경을 쓰기 전에 거부해요.
필요하면 생애주기 도입 전에 ID를 전환하거나, 기존 ID를 유지해요. 기록을 손상시키는 부분 전환은
허용하지 않아요.

Refine으로 활성 Seed의 새 세대를 만드는 경우에도 새 파일 생성만으로 기존 자식을 새 세대로
옮기지 않아요. 필요한 관계 변경을 명시적으로 승인받고 양쪽 파일을 검증해요. 종료된 Seed의
선택 항목을 재사용할 때는 새 Seed를 만들고 이전 완료 근거·승인을 새 작업의 증거로 복사하지
않아요. 원본 파일은 동결해 두고 새 파일에서 출처를 가리켜요.

## 발견과 소비

`seed-relations.py metadata <seed> --json`은 제목·짧은 목표·생애주기·종료 이유를 먼저 보여줘요.
`walk`는 관계와 적용 가능 여부를 함께 반환하며, 종료 노드를 제거하지 않아요. 본문이 실제
관련될 때만 `read <seed> --json` 또는 필요한 파일 범위를 읽어요. 메타데이터 계산을 위해
파일을 파싱하는 것과 모델 문맥에 원문 전체를 주입하는 것은 달라요.

소비 스킬은 Seed 본문을 Read/cat하기 전에 이 명령을 실제 실행해요. `walk`나 `read --json`은
이 metadata 호출을 대신하지 않아요(`read --json`은 본문을 포함해요). 경로가 이미 주어졌거나
파일 내용을 읽어 상태를 알아낼 수 있어도 순서를 바꾸지 않아요. 명령 실패는 상태 미확인과
구별해서 보고하고 본문 읽기·적용을 보류해요. 정적 문구 검사는 실제 실행 증거가 아니며,
실행 검증은 metadata 도구 호출이 본문 호출보다 앞서는지와 승인 전 파일 보존을 확인해요.

next-goal은 `eligibility`를 먼저 적용한 후 코드 근거로 남은 일을 판단해요. unknown/paused/
closed와 철회·영향 불명 항목은 자동 후보에서 제외해요. build-spec과 unknown-discovery도
동일 계약을 사용하고, 과거 Seed를 현재 요구사항으로 자동 승격하지 않아요.

session-close 연동은 local-harness 소스에서 별도 변경·검증해요. claude-kit은 local-harness가
없어도 이 파일과 공통 검증기로 동작해요. 소스 수정·설치 갱신·새 런타임 적용은 별개이며,
이번 소스 작업으로 사용자 설치 캐시나 personal skill을 자동 갱신하지 않아요.
