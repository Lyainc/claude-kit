# 문서 편집 최소 개편 제안과 개발 전 검증 상태 (#824)

관련 이슈: [#824](https://github.com/Lyainc/claude-kit/issues/824)

**권고는 기존의 강한 제작 프롬프트에 짧은 편집 지침을 더하고, 실질적인 내용 제외가 필요할 때만 검토·선택·보관·복원을 적용하는 것이다.** 이번 비교에서 읽는 순서와 배치의 개선 사례는 관찰했지만, 사용자 재수정 감소와 제외·복원 절차의 추가 효용은 입증하지 못했다. 스킬 구현의 착수 판단은 보류한다.

이 문서는 리뷰할 제안과 관찰 기록이다. 활성 Seed나 승인된 구현 명세가 아니며, 병합해도 스킬 계약·트리거·설치·기존 검토 절차가 바뀌지 않는다. #824의 큰 재설계 방향을 바로 구현하기보다 작은 후보의 효용부터 확인하자는 후속 제안이며, 이슈의 최종 결정을 대체하지 않는다.

## 1. 사용자 요구와 제안의 상태

| 상태 | 내용 |
|---|---|
| 사용자 확인 | 처음의 짧은 제작 프롬프트가 효과적이었다. 대화 마지막의 긴 HTML 편집 프롬프트는 Codex가 요약해 만든 것으로 성능이 낮았다는 사용자 보고 |
| 사용자 확인 | Claude Code에서 직접 HTML 제작, artifacts 경유 없음, 디자인 시스템은 제공하지 않음 |
| 사용자 승인 | 실제 HTML 2개로 A/B/C 비교, 제작 호출 최대 12회, 리뷰 1라운드, 실질적 제외 때만 선택·보관·복원 |
| 사용자 승인 | 프로젝트의 담당·마감 상세표와 서베이 36문항 전문을 제외 후보로 등록. 복원 시험 단위는 담당표 전체와 WRK 접기 컴포넌트 |
| 사용자 보고 | 기존 결과는 대체로 만족스럽고 개조식이 좋지만, 설명이 적고 정적인 느낌이 있음 |
| 현재 제안 | B의 작은 지침을 기본 후보로 삼고, 이번 두 문서는 상세를 같은 HTML에 유지하되 읽는 순서와 접기·이동을 개선 |
| 미결정 | 최종 유지·제외 선택, 선호하는 산출물과 반드시 고칠 항목, 스킬로 제공할 필요성, 이름·트리거·파일 구성 |

“둘 다 같은 HTML에 유지”는 문서의 현재 용도에 따른 작성자의 권고다. 사용자의 최종 제외 선택으로 확정된 것은 아니다. 사용자의 전반적 만족 보고도 이번 익명 A/B/C 평가나 재수정 감소의 증거로 바꾸지 않는다.

## 2. 현재 계약과 변경 후보의 경계

확인한 main은 `cd571879d75df2209f7b0cf27c958ba53b89efdd`(v6.0.2, 2026-10-11 조회)다. 실제 실행 계약은 아래 소스가 소유한다.

- [`doc-concretize`](../../thinking-tools/skills/doc-concretize/SKILL.md): 새로운 구조화 Markdown 작성과 별도 Agent의 최종 Verify. 검토자 입력은 조립된 문서·의도/독자·검토 항목이며 원자료 대조 계약은 아니다.
- [`doc-polish`](../../thinking-tools/skills/doc-polish/SKILL.md): 기존 Markdown 검사, 보고 기본값, `--fix`는 비의미적 수정만 허용한다.
- [호출 경계](../skill-boundaries.md): 실질적 재작성은 일반 편집이다. [아키텍처 경계](claude-kit-boundary.md)도 유지한다.

현재 스킬에도 관계 파악·용어 일관성 등의 기준은 있다. 추가 후보는 독자 목적에 따른 선별·읽는 순서·HTML 강조의 확인과, 필요할 때만 적용하는 제외·복원이다. “현재 스킬에는 의미 보존이 전혀 없다”거나 “모델이 좋아졌으므로 별도 검토가 불필요하다”는 결론은 근거가 없다.

| 담당 | 최소 후보의 역할 |
|---|---|
| 편집 지침 | 원문의 요청·근거·조건·용어를 보존하면서 읽는 순서와 강조를 정함 |
| 사용 가능한 제작 도구 | HTML/CSS·인터랙션·제공된 디자인 시스템 구현 |
| 다른 사고 도구 | 결론의 타당성 재검토와 대안 탐색 |
| 한국어 윤문 | 요청된 경우 표현을 정리하되 내용·조건을 변경하지 않음 |
| 기존 검사 기능 | 사실·링크·저장소 일치 검사. 모든 편집 뒤 자동 호출을 강제하지 않음 |

## 3. 최소 편집 지침 후보 B

기존 프롬프트 A에 다음 정도의 지침을 추가한다. 새 스킬 본문으로 설치하거나 실행 계약으로 채택한 것은 아니다.

```text
독자가 이해하거나 판단할 핵심과 작성자의 요청을 먼저 드러내세요.
원문의 근거와 수치·단위·주체·기간·조건·예외·불확실성을 보존하고,
새 사실이나 결론을 보태지 마세요. 분량보다 판단 관련성에 따라 순서와
강조를 정하고, 중요한 조건은 기본 화면에서 읽히게 하세요.
같은 개념의 용어는 일관되게 쓰고 원인·조건·결과를 자연스럽게 연결하세요.
정해진 질문을 반복하지 말고 결과의 의미를 바꾸는 공백만 확인하세요.
디자인 시스템이 제공되었을 때 그 체계로 최종 문서를 완성하고,
생성 과정 설명은 넣지 마세요.
```

이번 비교에서 B는 원문 보존·순서·강조를 겨냥했다. 사용자 불만인 설명 부족에 대해서는 **사실이 다음 판단에 왜 연결되는지 설명하는 한두 문장**을 보강하는 후속 후보를 제안한다. 이 보강은 이번 B에 독립적으로 시험한 요소가 아니므로 효과를 관찰했다고 주장하지 않는다.

- 전개는 두괄식을 기본으로 하되 사용자 지정과 내용의 의존관계를 따른다. 승인 요청이 없는 문서에 새 요청을 만들지 않는다.
- 같은 단어의 반복과 같은 주장의 반복을 구분한다. 동의어 치환으로 개념을 흔들지 않고, 원인·조건·결과를 짧은 문장으로 끊어 나열하지 않는다.
- 불리한 사실과 한계도 보존한다. 선택된 입장 보존은 과장·불확실성 삭제를 허용하지 않는다.
- 핵심 공백은 질문하고 미해결을 표시한다. 내부 사정을 외부 일반론이나 추정으로 채우지 않는다.
- 도식·카드·표의 수를 일률적으로 제한하지 않는다. 각 요소가 관계·비교·순서를 설명하는지를 확인한다.
- 가독성은 실제 렌더에서 확인한다. 모바일에서 넘치지 않아도 도식 글자가 읽히지 않으면 실패다.
- 탐색 인터랙션은 필요한 상세로 이동하거나 펼쳐 읽는 역할로 제안한다. 새 시뮬레이션·애니메이션을 필수 기능으로 추가하지 않는다.

## 4. 조건부 절차 후보 C

C는 더 강한 문체나 디자인을 만드는 상위 단계가 아니다. 의미 있는 문단·도식·컴포넌트를 제외할 때 사용자가 통제하고 복원할 수 있게 하는 절차다.

1. 원본을 보존한 검토본에서 제외 후보와 영향을 문서 밖에 간단히 제시한다. 판단을 바꿀 중요한 조건·한계의 요지는 본문에 남긴다.
2. 사용자가 유지·제외를 선택한다. 후보 등록이나 무응답을 최종 제외 승인으로 처리하지 않는다.
3. 선택을 반영한 클린본을 만들고 실제 제외한 내용은 별도 보존 자료로 분리한다. 독자용 문서에 편집 흔적을 섞지 않는다.
4. 복원에 필요한 원래 위치·selector/ID·원문 단위와 관련 CSS/JS/자산 의존성을 작은 대응표로 남긴다. 새 범용 버전 관리 도구를 만들지 않는다.
5. 등록한 단위를 실제로 선택 복원하고 내용·배치·동작을 확인한다. 전체 원본 복사나 해시 일치만으로 선택 복원이 성공했다고 판정하지 않는다.

사소한 중복 제거·문장 연결·용어 통일에는 이 절차를 발동하지 않는다. 실질적 제외가 없으면 선택 질문이나 빈 부록도 만들지 않는다. C가 사용자 선택으로 새 정보를 얻으면 A/B에도 같은 정보를 주어 결과 품질과 절차 효과를 구분한다.

## 5. 이번 두 문서의 편집 권고

| 선택 | 중점 | 현재 권고 |
|---|---|---|
| 프로젝트 표 유지, 서베이 전문 별도 부록 | 핵심 전달본의 빠른 열람 | 경영진 전달 단계의 후보. 현재 서베이 합의 단계에서는 문항 확인이 번거로워질 수 있음 |
| 두 문서 모두 상세를 같은 HTML에 유지 | 문서 하나로 판단하고 필요할 때 상세 확인 | **현재 우선 제안**. 중요 정보부터 배치하고 상세는 뒤쪽·접기·이동으로 접근 |
| 둘 다 별도 부록 | 전달본 분량 축소 | 책임·마감과 실제 측정 내용을 다른 파일에서 찾아야 하므로 현재 이점이 작음 |

- 프로젝트: 두 업무 갈래와 도입 순서를 먼저 설명한다. 담당·마감 표는 해당 운영 절차 가까이에 유지한다. 큰 도식의 핵심 관계를 설명하는 문장을 보강하고, 좁은 화면에서도 읽히도록 구성한다.
- 서베이: 상세 승인 요청·현재 합의 쟁점 → 측정 목적과 판단 기준 → 문항 상세 순서로 구성한다. 전문은 같은 HTML 뒤쪽에 접기로 유지하되 중요한 정의·응답 조건은 기본 화면에도 남긴다.
- 위 권고는 원문의 현재 합의 단계에 근거한 편집 판단이다. 사용자의 최종 선택이나 실험으로 확정된 최선의 결과는 아니다.

## 6. 실제 비교 근거와 한계

### 자료와 평가 방법

실제 HTML 두 개를 원문으로 A/B/C 각 1회 제작했다. 이전 작성자료·당시 전체 제작 입력·모델은 제공되지 않았다. HTML에 기재된 사실의 외부 타당성은 검증하지 않았다. 합성 자료를 실제 자료의 효과로 보고하지 않았다.

A의 사용자 프롬프트 원문은 다음과 같다. `조식`·`AST-STE100` 표기는 그대로 보존하고, 모든 안에 개조식·쉬운 어휘·명확한 주체와 동작·일관된 용어의 한국어 원칙으로 해석하는 공통 조건을 적용했다. 영어 표준 준수를 주장하지 않았다.

```text
조식으로 문장 편집. 불필요하게 단문을 반복하지말것, 중언부언 금지, AST-STE100으로 설명, 도식화 적극 사용하되 단순 테이블만 나열하지 말것, 직관적이고 간결하게, /humanize-korean:humanize 사용해서 윤문, 핵심과 본질에 집중, 불필요한 subtitle, 캡션, 부연설명 제거, 단일 문서만으로도 완결성있게(결과물을 받는 사람은 참고 문서의 존재를 모르기 때문에 외부 문서를 참고로 넣지 말 것), 디자인시스템이 있는경우 디자인시스템 사용,
```

| 안 | 적용 내용 |
|---|---|
| A | 사용자 기존의 짧은 프롬프트 그대로 |
| B | A + §3의 짧은 지침 |
| C | B + §4의 조건부 절차 |

부모 모델은 `claude-sonnet-5-5`, 실제 윤문 하위 모델은 플러그인의 `claude-opus-5-5`였다. `humanize-korean:humanize` Skill과 하위 Agent 실행을 확인했다. 디자인 시스템 없음, Claude Code 직접 파일 제작, artifacts 경유 없음의 조건이다.

생성 전에 실제 원문에서 의미 체크 30개를 고정했다. 별도 익명 평가자는 생성 프롬프트·안 매핑·notes 없이 원문과 체크 목록을 대조했다. 6개 산출물의 90개 체크 중 **89 충족, 1 부분, 0 실패**였다. 이는 모델 평가이며 사용자의 비교 평가나 통계적 효능 검증이 아니다. C의 검토 영역이 형식상 드러날 수 있어 완전한 눈가림을 보장하지 않는다.

실제 headless Chromium에서 1280×900과 390×844로 렌더하고 외부 요청을 공통 차단했다. 원본 프로젝트와 A는 1440px 최소 폭이고, 원본 서베이부터 13개 접기 요소가 있었다. 서베이 A/B/C의 접기·펼치기, 앵커 대상, 인쇄 전 펼치기가 동작했으며 페이지 JS 오류는 없었다.

프로젝트 A/B/C 모두 인터랙션이 없다. “정적 느낌이 해결됐다”는 결론은 낼 수 없다. 서베이의 순서 변경은 관찰했으나 독자의 이해 시간·사용자 재수정 감소는 측정되지 않았다. HTML 어디엔가 조건이 남아 있다는 사실과 기본 화면에서 조건이 잘 보인다는 평가는 별개다.

### 보존과 증거 접근

원본 HTML은 초기 복사본과 바이트가 같다. 확인한 기존 29개 worktree의 HEAD·dirty 상태·내용과 stash, vault의 HEAD·dirty 내용은 같다. vault 전체 clean 파일을 해시한 검사는 아니다. 기존 PR #841/#842/#843/#845/#846은 변경하지 않았다.

설치된 스킬 payload는 같지만 네이티브 실행의 사용 표식과 설치 등록 파일 해시가 바뀌었다. 등록 파일의 변경 필드·주체는 확인되지 않았고, 동시 세션 상태를 임의로 되돌리지 않았다. “캐시 전체 불변”은 충족으로 표시하지 않는다.

원본·생성 HTML·스크린샷·원문 대조·실행 영수증은 내부 업무 자료로 로컬에 보존한다. 이 PR에는 원문·스크린샷·전체 로그·설치 등록 내용·머신 경로를 게시하지 않는다. 원문 해시는 다음과 같다.

| 자료 | SHA256 |
|---|---|
| 프로젝트 원문 HTML | `2ebbc8ecea058307bf5ae797f2e3d4d7f06a28b22a576774909fc08351760dbe` |
| 서베이 원문 HTML | `3118fe758c2c1cc4176738e027e9a37af41925a275d24a8db48ec6919b9fe321` |

공개 PR의 집계만으로 원문 보존이나 시각 개선을 독립 재현할 수는 없다. 자료에 접근 가능한 리뷰어는 별도로 전달받은 로컬 비교 화면·원문·영수증을 함께 대조한다. 자료를 못 읽으면 관련 판정은 미확인으로 남긴다.

## 8. 후속 Claude 리뷰 요청

다른 열린 PR과 함께 리뷰하더라도 이 제안의 판단은 별도로 기록한다. 구현·설치·개명·merge를 리뷰에 포함하지 않는다.

1. #824, 이 제안, 현재 두 스킬 계약을 대조하고 확인된 요구·관찰·작성자의 추론·미검증 가설을 구분한다.
2. 작은 B 지침에 기존 프롬프트 대비 추가 가치가 있는지 반박한다. 기존 규칙의 반복만 남았으면 그것도 명시한다.
3. 설명 연결 보강과 같은 HTML 내 상세 유지가 목적에 맞는지 검토한다. 이 권고를 사용자 승인이나 실험 결과로 바꾸지 않는다.
4. C를 선택적 절차로 둘 근거와 생략 조건을 확인한다. 클린본·부록·복원 미실행을 성공으로 판정하지 않는다.
5. 로컬 자료에 접근할 수 있을 때 원문·익명 대조·렌더·metrics를 직접 확인한다. 시간 교란, 부분 눈가림, 한도 중단, cache bookkeeping 변화를 숨기지 않는다.
6. 기존 격리 Verify·사실 검사·일반 편집의 경계를 약화하는 제안이 있는지 확인한다.
7. 결과는 **작은 후보 추가 검증 / 미채택 / 자료 부족으로 판정 보류** 중 하나와 근거, 필요할 때 최소 수정안으로 작성한다. 개발 착수를 권한다면 미충족 조건을 어떻게 해소했는지 함께 밝힌다.

이 PR의 완료는 리뷰할 제안의 제출이다. #824의 효용 판정과 개발 전 완료 조건은 아직 충족되지 않았다.
