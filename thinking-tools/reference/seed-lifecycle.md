# Seed 생애주기 계약

이 문서는 #814의 공통 계약이에요. build-spec이 생성·변경을 소유하고, 종료 루틴은 이 계약을
사용해 승인된 종료 처리를 수행해요. Seed가 생애주기 원본이고, 관계 조회·next-goal·Seed board는
그 원본을 읽어요. UI 캐시나 GitHub 이슈 상태로 Seed 상태를 추정하지 않아요.

## 상태와 적용 범위

| 상태 | 의미 | 요구사항을 작업에 적용하는 조건 |
|---|---|---|
| 생애주기 없음 | 상태 미확인인 기존 Seed | 관련 본문은 읽을 수 있지만 적용 전 사용자 확인 필요 |
| `active` | 사용자가 활성화한 요구사항 | 현재 요청 범위에 속하고 철회·보류되지 않은 항목만 |
| `paused` | 재개 가능한 일시중단 | 사용자가 재개를 승인하고 `active`로 전환한 뒤 |
| `closed` | 종료된 결정 기록 | 자동 재개 금지. 선택한 요구사항을 새 Seed로 옮겨 별도 승인 |

경로를 명시하거나 그래프에서 발견한 것, next-goal 후보를 제안한 것만으로는 활성화·재개·범위
확장이 승인되지 않아요. 종료된 Seed는 결정 이유 조회, 충돌 검사, 설계 재사용에 계속 사용할 수
있어요. 이후 코드 변경은 과거 종료 결과를 자동 재판정하거나 변경하지 않아요.

## 저장 형식과 전이

템플릿 `skills/build-spec/templates/SEED_SPEC.yaml`이 필드 허용 목록을 소유해요.
아래 `{id, refs}` 표기는 필드 설명이에요. 실제 목록 항목은 들여쓴 block YAML로 작성해요.
별칭·태그·앵커·중첩 flow mapping은 지원하지 않으며 검증기가 명시적으로 거부해요.

- `lifecycle.state`: `active`, `paused`, `closed`.
- `lifecycle.outcome`: active/paused에서는 null, closed에서는 `completed` 또는 `discontinued`.
- `reason`, `approved_by`: 전환 이유와 실제 사용자 지시·확인 근거. 에이전트가 승인을 만들어
  적으면 안 돼요. 신규 활성화도 인터뷰에서 확정된 요청을 근거로 기록해요.
- `evidence.commit`: 검증 대상의 전체 Git SHA. 기록을 추가하는 커밋의 SHA와 구분해요.
- `evidence.items`: `{id, refs}` 목록. 각 refs는 그 항목을 확인한 코드·테스트·문서 위치 또는
  실행 결과 링크예요. 테스트를 실행하지 않았으면 실행했다고 쓰지 않아요.
- `withdrawn`: `{id, reason}` 목록. 원래 항목의 ID와 내용은 그대로 두고 철회만 별도 기록해요.

신규 Seed는 사용자가 확정한 요구사항으로 활성화해요. 미완성 초안의 조기 출력이 활성화 승인까지
포함하지 않으면 `paused`로 작성해요. 기존 상태 미확인 Seed는 사용자 확인 후에만 전환해요.
active ↔ paused, active/paused → closed는 실제 승인에 따라 처리해요. closed → active/paused는
허용하지 않아요. 종료 결과·완료 근거는 동결하고 새 작업에는 새 Seed와 출처를 사용해요.

`completed`는 철회하지 않은 **모든 constraints와 success_criteria**가 지정 커밋에서 충족되고,
항목별 근거가 있을 때만 가능해요. 남은 항목이 하나도 없이 전부 철회된 경우, 일부만 충족한 채
종료한 경우, 미충족 항목을 다른 Seed로 이관한 채 종료한 경우는 `discontinued`예요.
이관·이슈 닫힘·PR 병합은 그 자체로 충족 근거가 아니에요. 진행률·작업 일지·실행 로그는 계속
금지해요. 생애주기는 현재 결정 한 건이며 전환 이력을 append하는 배열이 아니에요.

## 승인과 변경 절차

1. 이름이 주어진 Seed만 메타데이터부터 확인해요. 관련 항목과 현재 코드·테스트를 읽고 처리안을
   만들어요. 발견, 읽기, 후보 제안, 요구사항 적용은 서로 다른 행위예요.
2. 상태 전환·철회·자식 영향·재연결을 구분해 제안해요. 기존 종료 확인과 함께 승인받을 수 있고,
   사용자가 이미 정확히 지시한 철회는 다시 묻지 않아요. 응답이 없으면 변경하지 않아요.
3. 수정 전 파일을 임시 파일에 보존하고 필드 값을 교체해요. 철회 항목은 원문을 보존해요.
4. `seed-lifecycle.py check <seed> --before <prior-file>`와 `seed-relations.py check <seed>`를
   실행해요. 검증 실패 시 수정안을 고치고, 외부 저장소 수정이 필요하면 그 위치를 보고해요.
5. Claude Code는 편집 훅도 사용하고 Codex는 동일 검증 명령을 명시적으로 실행해요. 기록된
   승인 문자열이 실제 인간의 승인인지 검증기가 판정할 수는 없어요. 에이전트가 대화 근거를
   확인해야 하고, 임의 파일 읽기나 도구 밖 편집까지 기술적으로 차단한다고 주장하지 않아요.

## 철회 영향과 관계

### 관계의 세 종류

항목과 관계는 층이 달라요. `acceptance-N`(완료 기준, `success_criteria` 섹션의 id)과
`constraint-N`(경계 조건)은 한 Seed 안의 항목이고, 아래 세 관계는 Seed 사이를 이어요. 관계마다
가리키는 단위가 달라요. `refines`는 "다듬는다"가 아니라 "부모의 완료 기준을 이행한다"는 뜻이에요.

판별 질문은 하나예요. **"이 Seed가 끝나지 않으면 다른 Seed가 약속한 완료 기준 중 하나가 미완인가?"**

| 종류 | 판별 | 표현 | 가리키는 대상 | 효과 |
|---|---|---|---|---|
| 자식 | 부모의 완료 기준을 나눠 맡는다 | `parent` + 부모의 `acceptance-N`을 하나 이상 담은 `refines` | 부모의 `acceptance` id | 부모 완료를 막고, 부모 철회 시 재검토 대상이 돼요(자동 철회 아님) |
| 선행 | 다른 Seed나 그 항목이 먼저 끝나야 시작할 수 있다 | `depends_on` | Seed 전체(`a.yaml`) 또는 항목 하나(`a.yaml#acceptance-1`) | 이 Seed의 시작만 막아요 |
| 참조 | 다른 Seed의 결과나 규칙을 따르거나 관련만 있다 | 필드 없이 본문에 `<seed-slug>/constraint-N`처럼 인용 | 인용한 항목 | 막거나 전파하지 않아요 |

**부모 범위 확장.** 새 Seed가 부모 범위에 속해야 하는데 맡을 부모 완료 기준이 없으면, 소속만으로
자식을 만들지 않아요. 사용자가 부모의 약속을 넓히기로 하면 부모에 `acceptance-N`을 추가하고, 새
Seed는 그 id를 `refines`하는 자식이 돼요. N은 철회된 항목을 포함해 부모에 있는 모든 `acceptance` 번호보다
큰 다음 번호예요. 빈 번호나 철회된 번호는 다시 쓰지 않아요. 부모 개정과 자식 연결은 각각 승인받고, 부모
개정은 그 자식 Seed를 실제로 쓰는 단계에서만 해요. 자식 연결이 거절되거나 Seed를 쓰지 않고 끝나면
부모도 고치지 않아요. 이 제안은 같은 레포의 `active` 부모에만 해요. 생애주기가 없는(unknown) 부모는
사용자 확인이 먼저고, `paused` 부모는 재개 승인이 먼저예요. `closed` 부모는 고치지 않으며 선택한
요구사항을 출처를 고정한 새 Seed로 옮겨요. 다른 레포 부모는 여기서 고칠 수 없으니, 그 레포에서 항목을
추가하기 전까지 이 Seed는 선행이나 참조로 두어요. 존재하지 않는 id를 `refines`하지 않아요. 부모 범위를
넓히지 않는다면 선행이나 참조예요. 기반을 사용하기만 하는 Seed는 기반의 형제가 되고 `depends_on`으로 기반을 가리켜요.

**자식은 자기 조상 Seed 전체를 `depends_on`하지 않아요.** 부모는 자식이 닫혀야 완료되고 자식은 선행이
끝나야 시작하니, 둘을 함께 걸면 서로를 기다려요. 부모의 일부 항목이 먼저 필요하면 그 항목을 가리켜요
(`depends_on: [docs/specs/a.yaml#acceptance-1]`). 항목 단위 선행은 그 항목만 기다리므로 교착이 아니에요.
단, 이 Seed나 그 후손이 `refines`하는 항목을 가리키면 그 항목은 이 Seed가 시작해야 충족되니 다시 교착이에요.
`seed-relations.py check`는 조상 Seed 전체를 가리키는 선행, 대상 항목이 없거나 철회된 선행, 이 Seed나 후손이
이행하는 항목을 가리키는 선행을 MISMATCH로 보고해요. 서로 다른 항목끼리의 엣지는 교착으로 보지 않아요.
충족 여부는 Seed에 쓰지 않아요. next-goal이 대상 항목의 `measurable_via`를 저장소에서 관찰해 판정하고,
대상 Seed가 `closed/completed`면 충족이에요. `measurable_via`가 없으면 미확인이고, 대상 항목이 철회되면
재검토 대상이에요. 항목 단위 선행도 사용자가 말할 때만 기록하고 추론하지 않아요.

**자식에게 적용되는 부모 제약.** 자식은 부모의 완료 기준을 나눠 맡으므로 부모의 `hard: true`
제약이 그대로 적용돼요. 자식이 이를 완화해야 하면 부모를 개정해요. `hard: false` 제약은 자식 본문에
인용했을 때만 적용돼요. 부모가 조상에게서 받는 hard 제약도 같은 방식으로 자식에게 이어져요. 이 규칙은
연결할 때 부모와 읽을 수 있는 조상의 hard 제약을 보여 주고 충돌을 확인하는 인터뷰 규칙이에요. 읽을 수 없는
파일의 제약은 없다고 보지 않고 미확인으로 표시해요. 두 Seed 제약의 의미 충돌을 검증기가 판정하지는 않아요.

부모의 제약을 따르는 것은 부모를 구성하는 것이 아니에요. 그래서 version 3의 `refines`는
부모의 `acceptance` id만 담고, 부모가 있으면 하나 이상이어야 해요. 해당하는 부모 완료 기준이
없으면 자식이 아니라 선행이나 참조예요. `refines_map`은 version 3에서 쓰지 않아요. 부모가 없는
독립 Seed의 `refines`, `link_reason`은 비워요. 이전 부모 항목은 고정된 `provenance`로 보존하며,
현재 부모의 항목 참조로 남기지 않아요.
자식 연결의 부모가 바뀌면(독립 전환이나 재연결) `provenance`에 이전 부모가 실제로 해석된 파일(구형
관계는 `-vN` 최신 세대 해석 결과), 전체 커밋 SHA, 이전 `refines` 항목 전부를 담은 행이 있어야 해요.
`seed-lifecycle.py check --before`와 편집 훅이 이 행 없이 출처를 버리는 전환을 거부해요. 참조로 읽히는
version 2 연결을 정리하는 경우(부모를 지우고 `depends_on`이나 본문 인용으로 바꾸는 경우)는 구성 관계가
아니었으므로 이 고정을 요구하지 않아요.

**부모 완료 규칙.** 부모를 `closed/completed`로 전이할 때, 같은 레포의 자식(위 정의의 자식)이
모두 `closed`여야 해요. 열린 자식이 있으면 전이를 거부하고 그 자식을 보고해요. 자식이
`discontinued`면 부모는 그 자식이 맡은 완료 기준을 직접 충족한 근거를 대거나, 그 기준을 철회하고
`discontinued`로 닫아요(근거 규칙은 위 `completed` 조건 그대로예요). 다른 레포 자식은 여기서
판정하지 않아요. 이 검사는 전이 시점에만 하며, 이미 닫힌 Seed를 다시 판정하지 않아요.

**철회 영향.** 자식에게만 전파되고 참조에는 전파되지 않아요.

- 부모 전체 철회는 자식 모두를 재검토 대상으로 만들어요. 자식을 자동 철회하지 않아요.
  재검토 표시는 재개 전 확인을 뜻하므로 `active`·`paused`·`unknown` 자식에 붙이고, 이미
  `closed`인 자식은 기록으로 두어요. 부모 검증 실패도 같은 기준으로 표시해요.
- 일부 철회는 철회된 `acceptance`를 `refines`한 자식만 재검토 대상으로 만들어요. 다른 유효 항목만
  맡은 자식은 계속 후보가 될 수 있어요. 자식 내부 항목 단위의 부분 제외는 하지 않아요.

**version 2 읽기.** 기존 version 2 Seed는 고치지 않고 이렇게 읽어요. `refines`에 `acceptance` id가
하나 이상 있는 `parent` 연결만 자식이고, 나머지(`constraint` id만 있거나 비어 있음)는 참조예요.
자식의 `refines` 안에서도 `acceptance` id만 철회 영향에 쓰고, `refines_map`은 형식만 검증하고
판정에 쓰지 않아요. 참조로 읽힌 연결은 차단하지 않으며 자동으로 `depends_on`으로 바꾸지 않아요.
정말 먼저 끝나야 하는 관계만 사용자 승인으로 `depends_on`을 추가해요.
- 재연결은 별도 사용자 승인 후 부모·자식 양방향 링크를 함께 검증해요. 철회 승인은 재연결
  승인이 아니에요. 적절한 부모가 없으면 독립 Seed로 유지하고 이전 출처를 보존해요.
  유효한 자식의 소속이 부적절해졌다면 다른 적절한 Seed로 옮기는 안을 먼저 제안해요.
  새 부모는 실제로 묶어 관리할 필요가 있을 때만 제안하며, 확인 전 연결을 확정하지 않아요.
- `relations.transfers`의 `{seed, items}`는 자기 항목의 명시적 이관이에요. 도착 Seed에는
  `relations.provenance`로 원본의 정확한 파일·커밋·선택 항목을 남겨요.
- `relations.replaces`는 대체 파일을 명시해요. 출처 고정은 별도의 `provenance`가 맡아요.

## 버전 해석과 호환

신규 관계는 `relations.version: 3`이며 parent/children/depends_on/replaces/transfers는 정확한
파일 경로를 가리켜요. `depends_on`만 `#<로컬 항목 id>`를 붙여 항목 하나를 가리킬 수 있어요. version 3은 위 "관계의 세 종류"를 따르고, version 2는 같은 경로 규칙에
위 "version 2 읽기"를 적용해요. version 2 파일을 3으로 올릴 때는 자식·선행·참조를 실제로
검토해서 승인받아요. 일괄 전환은 하지 않아요. `provenance`는 `{seed, commit, items}`로 파일과 커밋까지 고정해요.
고정한 행은 이후 편집에서도 같은 파일·같은 커밋을 가리키는 행으로 남아야 하고 items만 늘릴 수 있어요. 경로 표기와 SHA 대소문자 차이는 같은 값으로 보고, 형식이 깨진 행은 글자 그대로 남아야 해요. 잘못 고정한 행의 교정은 다른 생애주기·부모 변경 없이 `lifecycle.approved_by`와 `reason`을 둘 다 새 값으로 남긴 변경으로만 해요. 검사기는 이 기록이 바뀌었는지만 보고 실제 사용자가 승인했는지는 확인하지 못하므로, 승인 없이 이 두 값을 바꾸면 안 돼요. `seed-lifecycle.py check --before`와 Claude의 Edit/Write 편집 훅이 이를 검사하고, 그 밖의 쓰기 경로는 `check --before`를 직접 실행해야 검사돼요.
역사적 출처를 조회할 때 해당 커밋을 읽고, 읽지 못하면 미확인으로 표시해요.

생애주기와 관계 버전이 없는 구형 관계만 기존 `-vN` 최신 세대 해석을 유지해요. 명시적
생애주기를 가진 대상이나 종료 기록을 새 세대로 조용히 바꾸지 않아요. 관계 전환 때는 실제
해결된 파일과 양방향 링크를 검토해서 version 3으로 기록해요. 일괄 전환은 하지 않아요.
구형 ID는 그대로 읽고, ID 전환은 기존 `seed-id-migrate.py`의 지원 범위와 검증을 먼저 확인해요.
역사적 커밋의 ID는 원본 표기 그대로 유지해요.
현재 ID 전환 도구는 생애주기·구조화된 항목 참조가 있는 파일의 이름 변경을 쓰기 전에 거부해요.
필요하면 생애주기 도입 전에 ID를 전환하거나, 기존 ID를 유지해요. 기록을 손상시키는 부분 전환은
허용하지 않아요.

Refine으로 활성 Seed의 새 세대를 만드는 경우에도 새 파일 생성만으로 기존 자식을 새 세대로
옮기지 않아요. 필요한 관계 변경을 명시적으로 승인받고 양쪽 파일을 검증해요. 종료된 Seed의
선택 항목을 재사용할 때는 새 Seed를 만들고 이전 완료 근거·승인을 새 작업의 증거로 복사하지
않아요. 원본 파일은 동결해 두고 새 파일에서 출처를 가리켜요.

## 발견과 소비

`seed-relations.py metadata <seed> --json`은 제목·짧은 목표·생애주기·종료 이유를 먼저 보여줘요.
`walk`는 관계와 적용 가능 여부를 함께 반환하며, 종료 노드를 제거하지 않아요. 본문이 실제
관련될 때만 `read <seed> --json` 또는 필요한 파일 범위를 읽어요. 메타데이터 계산을 위해
파일을 파싱하는 것과 모델 문맥에 원문 전체를 주입하는 것은 달라요.

소비 스킬은 Seed 본문을 Read/cat하기 전에 이 명령을 실제 실행해요. `walk`나 `read --json`은
이 metadata 호출을 대신하지 않아요(`read --json`은 본문을 포함해요). 경로가 이미 주어졌거나
파일 내용을 읽어 상태를 알아낼 수 있어도 순서를 바꾸지 않아요. 명령 실패는 상태 미확인과
구별해서 보고하고 본문 읽기·적용을 보류해요. 정적 문구 검사는 실제 실행 증거가 아니며,
실행 검증은 metadata 도구 호출이 본문 호출보다 앞서는지와 승인 전 파일 보존을 확인해요.
Claude Code는 `hooks/seed-read-guard.sh`가 같은 기록에서 metadata 없이 Seed 본문을 Read/cat하는 호출을 Seed당 한 번 거부하고, Codex에는 이 훅이 없으며 Bash 판정은 휴리스틱이라 모든 읽기를 막지 않아요.

next-goal은 `eligibility`를 먼저 적용한 후 코드 근거로 남은 일을 판단해요. unknown/paused/
closed와 철회·영향 불명 항목은 자동 후보에서 제외해요. build-spec과 unknown-discovery도
동일 계약을 사용하고, 과거 Seed를 현재 요구사항으로 자동 승격하지 않아요.

session-close 연동은 local-harness 소스에서 별도 변경·검증해요. claude-kit은 local-harness가
없어도 이 파일과 공통 검증기로 동작해요. 소스 수정·설치 갱신·새 런타임 적용은 별개이며,
이번 소스 작업으로 사용자 설치 캐시나 personal skill을 자동 갱신하지 않아요.
